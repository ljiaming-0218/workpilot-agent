# P3 持久化后台任务：实现前核对（2026-10-31）

## 当前链路和问题

`POST /agent/runs/async` 在请求内运行 Router/Planner，调用
`prepare_agent_run()` 提交 `agent_runs` 和服务范围后，通过 FastAPI
`BackgroundTasks` 在 API 进程中执行。进程退出后没有持久队列负责重新领取。

现有 `agent_runs.status` 没有排队状态；任务准备函数自行提交事务。
`multi_agent_service.py` 在执行中多次提交 Trace；各调查分支使用独立
Session，`registry.py` 也会提交工具调用日志。最终报告、Trace、工具调用
和审批 checkpoint 都直接关联同一个 `run_id`。因此只在最终报告更新时检查
领取令牌，不能防止旧尝试写入日志或 Trace，也不能避免重试的证据混杂。

`RunEventBroker` 是进程内内存，独立 Worker 发布的事件不能被 API 进程读取。
当前 SSE 在没有内存事件且 run 为 running 时返回
`LIVE_STREAM_UNAVAILABLE` 终态，不能直接接入持久队列。审批 checkpoint
以 run 为主键，应用启动时还会执行恢复协调；并发 Worker 必须与之协调。
告警入口当前同步执行，按 P4 范围后续接入，不在 P3 偷换其语义。

当前配置数据库只读连接检查成功，服务报告 `TiDB v8.5.3-serverless`。
在随机命名、用后删除的隔离探针表上，双连接条件更新竞争只有一个成功；
队列原型验证了幂等唯一约束、竞争领取、续租、过期恢复、旧令牌拒绝、
尝试历史和不安全任务的到期失败。这是有限 smoke 检查，不代表已经验证
所有事务隔离、故障场景或其他 MySQL 版本。不得改动现有业务数据。

## 数据模型和边界

以下是待实现契约，不表示功能已经上线：

1. 以稳定的任务 ID 表示一次用户提交，保存创建人、团队、服务范围、
   原始请求、提交幂等键、请求指纹、队列状态、当前 attempt、租约和令牌。
   提交任务和服务范围应在同一事务中持久化，不能调用内部自行 commit 的
   `prepare_agent_run()` 后再单独入队。
2. 幂等键由客户端为每次主动提交生成；按用户和团队限定作用域，并建立
   数据库唯一约束。相同键及相同规范化请求返回原任务；不同请求返回 409。
   唯一约束必须覆盖并发首提交，不能仅靠先查再插。重试时仍要检查调用人
   对该任务和其全部服务的当前访问权限。
3. 每次领取生成独立 attempt 记录，包含序号、领取者、随机领取令牌、
   开始与结束时间、状态、失败原因；过期 attempt 不覆盖历史。不要暴露
   领取令牌给客户端、日志或模型。
4. 任务领取、到期回收、续租和发布最终结果使用数据库事务与条件更新；
   判断租约时使用数据库时间。令牌匹配之外还需检查状态和未过期；过期
   后的续租不能复活旧领取。有限重试耗尽后进入明确的失败状态。
5. 每个 attempt 的中间数据必须与其他 attempt 隔离。一个可行方向是让每个
   attempt 使用独立的执行 run、request_id 和 checkpoint，任务只通过经过
   令牌校验的原子操作发布当前有效 attempt；历史读取、Trace、工具调用和
   SSE 必须通过任务授权与选定 attempt 读取。旧执行 run 即使迟到写入，也
   不能成为当前报告或与新 attempt 的证据混合。此方向需要明确旧 API 的
   run_id 兼容方式、历史列表和审计保留规则后才能实施。
6. 独立 Worker 在每次开始执行时重新检查创建人团队成员资格和所有服务
   授权；任何客户端、LLM 或工具传入的范围都不能替代服务端范围。
   审批路径、checkpoint 恢复和授权撤销需要单独验证。
7. 进度使用数据库可跨进程读取的状态或事件，并保留 Last-Event-ID、断线
   恢复和明确终态语义；前端不能将等待领取、流中断等同于执行失败。
   当前内存 broker 不能作为持久状态的唯一来源。
8. 仅明确可安全重试的只读调查可在租约失效后自动重试，模型调用可能
   重复并产生费用。涉及外部副作用或审批后操作且结果未知时，必须停止
   自动重试并标记待核查；系统不承诺 exactly-once。

## 实施顺序与验收

1. 在隔离的 MySQL 和实际 TiDB 测试环境中验证竞争领取与事务语义，确定
   兼容的原子条件更新方案；设计可重复的增量迁移，不回填未知历史归属。
2. 增加任务、attempt 和幂等数据模型；让创建及领取实现事务闭环，并
   确保只读任务在租约过期后可有限重试。
3. 改造执行隔离、权限复核、审批和 Trace/工具日志读取；保证旧 Worker
   迟到时无法发布、覆盖、污染当前结果。不得在隔离完成前启用自动重试。
4. 增加独立 Worker 启动方式、跨进程进度及前端提交幂等键，并保留当前
   同步接口及已有数据的兼容性。
5. 验收同键同内容、同键不同内容、不同键同内容、两 Worker 竞争、进程
   中断与租约到期恢复、续租、旧 Worker 的迟到写入、尝试历史、权限撤销、
   审批及未知外部结果。检查迁移重复执行，并核对实际数据库上的行为。

## 当前实现进度

`backend/models/durable_job.py` 和 `backend/services/durable_queue.py` 提供
独立的队列数据模型与事务原语；`scripts/migrate_p3.py` 是仅创建两张新表的
增量迁移脚本，已在配置数据库连续执行两次通过。`scripts/smoke_p3_claim_db.py`
和 `scripts/smoke_p3_queue_db.py` 使用随机隔离表验证后清理。

每个 attempt 现在可通过 `durable_attempt.py` 领取独立执行 run，并在持有有效
租约时发布到原 run；旧 attempt 的迟到写入只影响自己的执行 run。启动前
重新检查身份和服务权限，发布等待审批状态时要求匹配且未过期的 checkpoint。
`durable_worker.py` 提供心跳、执行编排和有令牌的发布，`durable_agent_adapter.py`
适配现有 Agent。独立进程入口是 `scripts/run_p3_worker.py`；可重试任务只允许
进入只读 Multi-Agent 流程。

在 TiDB 的随机隔离表上，`scripts/smoke_p3_attempt_db.py` 检查了权限撤销、
独立 run、旧令牌不能发布、待审批 checkpoint 校验、心跳续租，以及使用
模拟 MCP 空响应的真实 Multi-Agent 和 Tool Registry 链路。脚本还启动并终止
一个探针 Worker 子进程，验证第二个 Worker 在租约过期后领取新 attempt。
调查工具使用模拟 MCP 响应，不调用真实模型；API 与审批恢复通过后续测试覆盖。

HTTP 异步提交、历史/Trace 读取、跨进程 SSE 和审批结果映射已增加受控接入，
默认 `P3_DURABLE_ENABLED=false`。隔离数据库 smoke 已验证提交幂等、内部 run
隐藏、跨团队拒绝、历史、Trace、SSE，以及 LangGraph 审批后模拟操作和重复
审批拒绝。并发 HTTP 同键提交、等待审批后跨进程恢复，以及已领取审批结果
未知时停止重试均通过；前端使用模拟 API
的 Chrome 交互检查通过。随后在真实本地 HTTP 服务与隔离 TiDB 数据上通过
Chrome 登录、Cookie、持久提交、Worker、原生 SSE 和完成态检查；调查执行
使用固定结果，业务数据列表使用空响应。
